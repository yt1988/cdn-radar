# 设计决定和否决过的方案

这里记录 CDN 雷达定下来的规则、为什么这样定，以及考虑过但没有做的方案。改界面、文案、测法之前先读一遍。最新的写在每节前面；没写日期的从开始就是这样。

## 测量

- **结果不能先错后对**（2026-11-05，站长定）。不先用第一次请求的往返时间显示、测完再改数字；页面上出现的数字就是最终的数字。
- **每家 CDN 的第一次请求只用来建连接，不计时**；之后 3 次复用这条连接，取中位数（`src/probe.mjs`）。所以页面加载时预先和最先测的几家建好连接（`<link rel="preconnect">`），不会改变测出的数值，只是结果来得更早（2026-11-06）。
- **不加缓存破坏参数**：CDN 对已缓存在边缘的地址直接作答，加了参数就会测到回源。
- **不判断「直连还是代理」**（2026-11-03，站长定）。曾经做过按出口 IP 给每家 CDN 标 D/P，误判太多（只对本站生效的代理规则、Cloudflare 退回本站 trace 等情况），已全部删掉。现在的做法：
  - 页面写明「结果反映的是你当前的网络和分流规则」；
  - 想单独测一种情况的用户，用「只测直连或只测代理」提供的远程规则集（`/rules/`），自己在代理客户端里分流。
  - 规则集只列测试用的域名，不包括本站域名，因为用户的代理客户端里本站常常要走代理。
- **不连接任何代理软件的接口**（Clash、Mihomo 等）。关于代理的一切推断，都只能来自浏览器自己能测到的东西。

## 结论区怎么排（2026-11-05，站长要求「聚焦重要信息，又不失准确，优雅、简洁、高效」）

- **每条信息只出现一次。** 距离、延迟、最远节点在统计卡片和下面的表格里，结论区不再重复这些数字，只写数字说明不了的事。
- **结论区一行一句，同一原因合并成一行，最多 4 行，按以下顺序：**
  1. 连不上的；
  2. 附近有节点却分到远处的；
  3. 节点不远但线路绕路的；
  4. 远节点的原因，按 Anycast 或 DNS 分组；
  5. 30 ms 以内的（不含远节点）。
- **原因行末尾是「为什么？」**，点开帮助里「为什么被分到很远的节点」那一条。完整解释放在帮助里，不放在主界面。
- **访客 DNS 服务器的信息单独一行，淡色小字放在结论区下面**，带 DB-IP 署名（它的许可要求）。这一行的位置事先留好，出现时页面不跳动。
- **结论标题说「远」时，结论区不能写「没有发现明显问题」**：说不出原因时，就写「把你分到了远处，用它的网站打开会慢一些」。
- 统计卡片的内容居中。

## 远节点归因（`lib.blame`，2026-11-04）

- **按 DNS 分配节点：** Akamai、CloudFront、Bunny、Wikimedia。**用 Anycast：** Cloudflare（含中国网络）、Fastly、Azure Front Door。只测延迟的几家不做归因。
- **怎么知道访客的 DNS 服务器：** 每次测试让浏览器解析一个本次专用的 `<token>-c.l.1ms.dog`（dns-test 的权威 DNS），接口返回是谁来查询的、在哪、有没有带 ECS。
- **以最早到达的那批查询为准（150 ms 以内）：**
  - 晚到的查询常来自同一运营商的其他出口，有时带着 ECS，但浏览器拿到的答案是最早那批给的。
  - 2026-11-04 实测联通：最早的查询不带 ECS，约 250 ms 后又来了带 ECS 的。dns 会话也确认，从权威端分不清这些晚到的查询是缓存、预取，还是回源。
- **ECS 分三种情况：**
  - 最早的查询带了 ECS：算带，远节点不是 DNS 造成的。
  - 都没带：按 DNS 服务器所在位置判断。
  - 只有晚到的查询带了：如实写「稍后的查询才带了你的网段」，对按 DNS 分配的 CDN 不下结论。
  - 否决的方案：dns 曾建议「同一解析器只要有一条带 ECS 就算带」，但晚到的那几条不是同一个解析器，会把远节点错判成「不是 DNS 造成的」。
- **「换个近处的 DNS 会更近」只在节点就在 DNS 服务器所在国家时才说。**
  - 如果 DNS 服务器、访客的出口、节点分在三个国家，多半是代理分流（CDN 的域名在代理那边解析，本站的域名是直连解析的），这时说「原因看不出」。
  - 2026-11-04 线上实测：联通的 DNS 服务器、日本的出口、比利时的 Akamai 节点。按旧规则会说「换 DNS 就好」，那是错的。
- **访客的 DNS 服务器信息只在当次测试里用**，不进分享链接、分享卡片和问题报告。

## 东京服务器（2026-11-04 起）

- **`1ms-cdn-watch`：** 每 10 分钟从东京按页面同样的测法测一遍，作为固定参照：东京这边也换了节点，说明是 CDN 自己在调整。
- **`1ms-cdn-ecs`：** 只做 CloudFront。Akamai 的权威 DNS 对我们带去的 ECS 一律按同一答案回复（scope 0，所有运营商都分到东京），因为它只认白名单里的解析器，这张表做出来没有意义，所以去掉了。
- **各运营商的代表网段**（`data/ecs-nets.json`）：取该运营商宣告的最大 IPv4 前缀中间那个 /24。这只是一个代表，不覆盖同一运营商在所有地区的情况，页面上写明了这一点。
- **考虑过但没做：**
  - 从东京对访客做 traceroute：测到的是东京到访客的反向路径，和访客到 CDN 的路径无关。
  - 从东京 ping 各节点：只代表东京，对访客意义不大。
  - 站长 2026-11-04 也否决了全站「从服务器主动探测访客 IP」这一类做法。

## 首屏加载（LCP）

- **LCP 落在哪：** 手机上落在结论区的文字上（随测量结果出现），桌面上落在首屏标题上。数据来自 1ms-shell 的 `npm run traffic`「LCP element per tool」，2026-11-06 的数据：手机上 `li.why` 占 45%，p75 约 5.1 s；桌面上 h1 占 84%，约 2.0 s。
- **规则（站长定，2026-11-05 和 11-06）：**
  - 只能让结果本身更早出现，也就是缩短测量开始前的等待；
  - 不加同尺寸的占位，也不先画一个更大的元素，这类做法只改变 LCP 算在哪个元素上，结果并没有更早出现；
  - 缩小结论的字号或行数属于界面改动，由站长决定。
- **已做：**
  - 在 `<head>` 里预加载 `pops.json`，测量不再等它（aa24810）；
  - 样式表内联进页面，页面脚本不再等外链样式表（1b03ddd）；
  - 最先测的几家 CDN 预先建好连接（1b03ddd）。
- **没做或待定：**
  - 先显示第一次请求的往返、测完再更新：不做，违反「结果不能先错后对」；
  - 语言选单引起的西里尔字体下载：由 Public 全站统一改；
  - shell 的统计脚本 `/metrics/`（186 KB，在慢速网络上抢带宽）：站长还没决定。

## 文案

- **写法按 1ms-shell 的 `docs/translation.md`：** 10 种语言各自从意思出发重写，繁体中文按台湾用语，先说结论。
- **CDN 节点的统一叫法：** zh-CN「节点」、zh-TW「節點」、ja「拠点」、de「Standort」，en、ko、es、fr、pt、ru 都用 data center（各自的语言写法）。英文不用 location，免得和「你的位置」混淆。
- **其他统一用词：** 往返时间统一叫「延迟」；按距离算出的下限叫「理论最低延迟」；绕路叫「绕路了」；「调度」不写在正文里，写成「把你分到」。Anycast 保留原词，第一次出现时加一句解释。
- **隐私说明必须和实际行为逐字对得上：** 本站只帮页面做三件事——根据 IP 判断大致位置、把节点代码换成城市名、看出访客用的 DNS 服务器——而且不保存测试结果。不写「不会向本站发送任何数据」这类不准确的话。

## 其他

- **地名表不随页面下发**：页面需要时向 Worker 的 `/places` 请求那几个代码对应的城市，`data/places.json` 只打包在 Worker 里（2026-11-03）。
- **分享用 1ms-shell 的公共分享组件**：分享卡片上最快的 3 家放大显示，缩到聊天软件的预览图大小也能看清。
- **CDN 子页面只测这一家 CDN**，页面上放一个「测全部」的链接回首页（1ms-shell 工具契约里关于子页面的规定）。
