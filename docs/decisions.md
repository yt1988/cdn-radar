# 测法、设计理由和测过的结论

这里记录 CDN 雷达在技术上定下来的规则、这样定的原因，以及测过、试过但没有采用的做法。改测法、结论或文案之前先读一遍。

## 测量

- **结果不能先错后对。** 不先用第一次请求的往返时间显示、测完再改数字；页面上出现的数字就是最终的数字。
- **每家 CDN 的第一次请求只用来建连接，不计时。** 之后复用这条连接计时 3 次，取中位数（`src/probe.mjs`）。所以页面加载时预先和最先测的几家建好连接（`<link rel="preconnect">`），不会改变测出的数值，只是结果来得更早。
- **不加缓存破坏参数。** CDN 对已缓存在边缘的地址直接作答，加了参数就会测到回源。
- **不按出口 IP 判断每家 CDN 走的是直连还是代理。** 试过，误判太多：比如只对本站域名生效的代理规则，或者 Cloudflare 的测试文件连不上时退回本站的 `/cdn-cgi/trace`。现在页面只写明「结果反映的是你当前的网络和分流规则」，想单独测一种情况的用户用远程规则集（`/rules/`），在代理客户端里自己分流。规则集只列测试用的域名，不包括本站域名，因为用户的代理客户端里常常要让本站走代理。

## 结论的一致性

- **结论标题说「远」时，结论区不能写「没有发现明显问题」。** 说不出原因时，就写「把你分到了远处，用它的网站打开会慢一些」。
- **同一家 CDN 不会同时出现在「远处」和「30 ms 以内」两行里。** 30 ms 以内那一行不列远节点。
- **访客 DNS 服务器的那一行带 DB-IP 署名。** 页面上显示由 DB-IP 定位出的国家或机构时，它的许可（CC BY 4.0）要求注明来源。

## 远节点归因（`lib.blame`）

- **按 DNS 分配节点：** Akamai、CloudFront、Bunny、Wikimedia。**用 Anycast：** Cloudflare（含中国网络）、Fastly、Azure Front Door。只测延迟的几家不做归因。
- **怎么知道访客的 DNS 服务器：** 每次测试让浏览器解析一个本次专用的名字，它的权威 DNS 记录下来是谁来查询的、在哪、有没有带 ECS（EDNS Client Subnet）。页面再向它取结果。在 1ms.dog 上用的是 `l.1ms.dog`。
- **以最早到达的那批查询为准（150 ms 以内）：**
  - 晚到的查询常来自同一运营商的其他出口，有时带着 ECS，但浏览器拿到的答案是最早那批给的。
  - 2026-11-04 实测中国联通：最早的查询不带 ECS，约 250 ms 后又来了几条带 ECS 的，来自其他 IP。
  - 从权威 DNS 这一端分不清这些晚到的查询是二级缓存、预取还是回源。
- **ECS 分三种情况：**
  - 最早的查询带了 ECS：算带，远节点不是 DNS 造成的。
  - 都没带：按 DNS 服务器所在的位置判断。
  - 只有晚到的查询带了：如实写「稍后的查询才带了你的网段」，对按 DNS 分配的 CDN 不下结论。
  - 没采用「同一解析器只要有一条带 ECS 就算带」：晚到的那几条来自其他 IP，不是同一个解析器，这样会把远节点错判成「不是 DNS 造成的」。
- **「换个近处的 DNS 会更近」只在节点就在 DNS 服务器所在国家时才说。**
  - 如果 DNS 服务器、访客的出口、节点分在三个国家，多半是代理分流：CDN 的域名在代理那边解析，本站的域名直连解析。这时说「原因看不出」。
  - 2026-11-04 实测：联通的 DNS 服务器、日本的出口、比利时的 Akamai 节点。按旧规则会说「换 DNS 就好」，那是错的。
- **访客的 DNS 服务器信息只在当次测试里用**，不进分享链接、分享卡片，也不进问题报告。

## 服务器上的定时任务（`server/`）

- **`watch`：** 从固定的一台服务器，按页面同样的测法定时测一遍。它是参照：服务器这边也换了节点，说明是 CDN 自己在调整；只有访客那边变了，多半是访客的网络或 DNS 的原因。
- **`ecs` 只做 CloudFront。**
  - Akamai 的权威 DNS 对带去的 ECS 一律给同一个答案（scope 0）。2026-11-04 实测，29 家运营商的网段全部分到东京，因为它只认白名单里的解析器，这张表没有意义。
  - CloudFront 按网段回答（scope 24），结果有区分度：同一天中国电信分到首尔、中国联通分到苏黎世、中国移动分到香港。
- **各运营商的代表网段**（`data/ecs-nets.json`）：取该运营商宣告的最大 IPv4 前缀中间那个 /24。它只是一个代表，不覆盖同一运营商在所有地区的情况，页面上写明了这一点。
- **测过但没采用：**
  - 从服务器对访客做 traceroute：测到的是服务器到访客的反向路径，和访客到 CDN 的路径无关。
  - 从服务器 ping 各节点：只代表服务器所在地，对访客意义不大。

## 首屏加载（LCP）

- **LCP 落在哪：** 手机上落在结论区的文字上。它随测量结果出现，而且同一原因合并的那一行会随着更多 CDN 测完而变长，每变长一次就产生一个新的 LCP 候选。桌面上落在首屏标题上。
- **规则：**
  - 只能让结果本身更早出现，也就是缩短测量开始前的等待；
  - 不加同尺寸的占位，也不先画一个更大的元素：这类做法只改变 LCP 算在哪个元素上，结果并没有更早出现，指标会误导人。
- **已做：**
  - 在 `<head>` 里预加载 `pops.json`，测量不再等它；
  - 样式表内联进页面，页面脚本不再等外链样式表；
  - 最先测的几家 CDN 预先建好连接。
- **实测**（手机、CPU 降速 4 倍、1.6 Mbps、150 ms RTT，wrangler dev）：
  - 预加载那一步，LCP 中位数 2,464 → 2,156 ms；
  - 内联和预连接那一步，首次渲染约 960 → 720 ms，测量开始约 1,100 → 810 ms。
- **不做：** 先显示第一次请求的往返、测完再更新，因为违反「结果不能先错后对」。

## 文案

- **写法：** 10 种语言各自从意思出发重写，不逐词翻译；繁体中文按台湾用语；先说结论。1ms.dog 的翻译规范在私有仓库 1ms-shell。
- **CDN 节点的统一叫法：** zh-CN「节点」、zh-TW「節點」、ja「拠点」、de「Standort」；en、ko、es、fr、pt、ru 用 data center（各自的语言写法）。英文不用 location，免得和「你的位置」混淆。
- **其他统一用词：** 往返时间统一叫「延迟」；按距离算出的下限叫「理论最低延迟」；绕路叫「绕路了」；「调度」不写进正文，写成「把你分到」；Anycast 保留原词，第一次出现时加一句解释。
- **隐私说明必须和实际行为逐字对得上：** 本站只帮页面做三件事——根据 IP 判断大致位置、把节点代码换成城市名、看出访客用的 DNS 服务器——而且不保存测试结果。不写「不会向本站发送任何数据」这类不准确的话。

## 其他

- **地名表不随页面下发：** 页面需要时向 Worker 的 `/places` 请求那几个代码对应的城市，`data/places.json` 只打包在 Worker 里，因为整个文件太大，而一个页面只用得到其中几个。
- **分享卡片上最快的 3 家放大显示：** 卡片缩到聊天软件预览图的大小时也要看得清。
